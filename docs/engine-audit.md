## Contracts

- Model version remains 2. Existing URLs without actions validate unchanged. `actions?: { at: number; type: "redrive" }[]` is optional, bounded to 24 ordered unique times in 0–32s, and restricted to the DLQ lesson. A scheduled action against an empty DLQ is an explicit no-op event.
- `Frame.outcome` and `Run.outcome` separate domain results from playback position: `pending`, `success`, `failed`, `recovered`, or `observing`. Ongoing traffic and policy lessons remain observations; reaching the end of their timeline does not certify success. A completed remote effect after caller timeout remains distinguishable in the outcome detail.
- Saga `attempts`/`completed` include both forward and compensating business actions. Separate counters record forward attempts/commits/errors and compensation attempts/commits.
- Disaster recovery records the planned duration separately from actual elapsed unavailability. The first validated recovery result freezes. A later injected fault is identified as another outage and does not rewrite the first measurement.
- Queue snapshots preserve `accepted = completed + pending + dead`. Repair and redrive never fabricate completion. Internal bounded-workload and worker hooks allow the connected journey to reuse this lifecycle; standalone lesson configuration and share URLs retain the same public shape apart from optional actions.
- The standalone breaker and journey use the same `circuit-policy.ts` threshold, cooldown, half-open, and result transitions. The caller must reserve at most one half-open probe in flight.

## Verified references

Official documentation was fetched and read during this pass:

- [How CloudFront delivers content](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html): CloudFront checks its cache, requests an origin object on a miss, receives the origin response, and forwards it to the viewer. Hits return from the edge. Regional edge caches are a documented additional layer; this lesson intentionally models one CloudFront cache boundary and S3.
- [Configuring SQS dead-letter queue redrive](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-dead-letter-queue-redrive.html): `StartMessageMoveTask` explicitly starts moving messages from the DLQ; fixing a consumer is not that action. Real SQS redrive is asynchronous, can have a configured rate, and assigns new message IDs and enqueue times.

## Evidence and limits

Event paths were checked across all 56 lessons under baseline, contrast, and fault/recovery configurations. Serial write-through, invalidation, and DLQ paths now include their actual application/source-queue intermediaries. `dispatch`, `replicate`, and `enqueue` can represent first-node fanout; consecutive recipients in those paths are not transport hops between recipients. Ring `membership` lists affected owners as context and has no transport edges. No fabricated recipient-to-recipient connections were added.

`node --import tsx --test tests/engine.test.ts` passes 77 tests after these changes. Added regressions use literal expected counts, times, paths, and statuses; they do not calculate expected results by rerunning the same engine. Tests also cover every lesson, immutable deterministic replay, URL compatibility, and queue accounting at each snapshot.

These are bounded educational simulations, not AWS performance predictions. The CDN model omits regional cache layers and streaming bytes. Redrive moves all quarantined work atomically within one simulated second, retaining a stable logical learning ID across receives; real SQS creates new transport IDs. Saga compensation succeeds once scheduled; compensation retries remain explained but are not simulated. Recovery models a single measured restore and clearly labels later faults. No live AWS service was called or provisioned.
